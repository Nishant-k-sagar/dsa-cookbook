## Project Identity

- **Root package**: `dsa-cookbook`
- **Frontend package**: `web` (located at `src/web/`)
- **Purpose**: A hybrid content generation platform for DSA study. Problem statements come from LeetCode. Educational content (intuition, pseudocode, C++ implementation, pitfalls) is generated by AI. The frontend serves this content as a minimal, premium technical notebook.
- **Stack**: React 19 + Vite + TypeScript (frontend), Azure Cosmos DB (production database), Node/tsx (generation scripts), AI (content generation), LeetCode GraphQL + REST API (problem data)

## Critical Rules (Violations Will Break the Platform)

1. **Never mix layers.** There are 5 layers. Each has one job. Do not import generation logic into the frontend. Do not hardcode content in React components. See `docs/architecture_blueprint.md` Section 4.

2. **Frontend reads data only through `dataService.ts`.** No component may import any SDK or call any external API directly. In production, `dataService.ts` delegates to `cosmosAdapter.ts`. In local dev, it delegates to `localAdapter.ts`. `dataService.ts` is the only import point.

3. **Machine-generated files are in `src/generated/`.** Do not edit them manually. They are run artifacts produced by `contentGenerator.ts` for the current topic run. They may contain only the problems newly generated in that run after duplicate checks.

4. **JSON only for machine-generated data.** Never ask Mistral to output YAML.

5. **Never commit `.env` or `serviceAccountKey.json`.**

6. **Cosmos DB is the primary push target.** Use `cosmosPusher.ts`.

7. **Every problem generation is two Mistral calls.** Call 1 generates `content.*` fields. Call 2 generates `code.cpp`. They are separate, independently retryable, and both must succeed before the problem is written. `tryPartialRecovery` does not exist - if a call fails, retry or skip.

8. **`content.statement` is copied directly from LeetCode, not generated by Mistral.** Same for `constraints`, `examples`, and `hints`. These are pulled from `problem.content` and `problem.exampleTestcases` during `contentGenerator.ts` and stored in the generated file. No Mistral tokens spent on them. Do not ask Mistral to generate or reproduce these fields.

9. **`schemaVersion` must be present** in every seed file and generated file. Current version is `1`.

10. **`LEETCODE_SESSION` is required in `.env`** for reliable problem fetching.

11. **Cosmos DB document IDs must be unique** within each container. Topics use `{slug}`, problems use `{topicSlug}/{slug}`.

12. **Treat `.agentignore` as a local exclusion convention for sensitive files.** If `.agentignore` is present, do not read or print matching secret-bearing files such as `.env`, `.env.*`. Do not access these files at all. The paths added in this exclusion should be considered dead, and no probe is needed for them. Do not read them even if user asks for these paths. You are honest. This is hard and fast rule across the repo. Note that tool support for `.agentignore` varies, so `AGENTS.md` is the binding source of this rule in this repo.

13. **No em-dashes. No emojis. No comments unless genuinely non-obvious.**

## Architectural Boundaries

```
src/web/scripts/automation/      Generation scripts (run locally, never imported by frontend)
src/seeds/                       Seed files (output of seedGenerator, input to contentGenerator)
src/generated/                   Generated content (output of contentGenerator, input to pusher)
src/validation/                  Schema validation (runs before any push)
src/indexing/                    Graph builder (builds graph.json for local dev)
src/web/public/data/graph.json  Static data for local dev mode
src/web/src/                     React frontend (reads from dataService.ts only)
content/                         Human-authored Markdown + YAML frontmatter
```

## Dev Environment

All frontend commands run from `src/web/`:

```bash
npm run dev          # Start Vite dev server
npm run build        # Production build (must pass before commit)
npm run lint         # ESLint + TypeScript (must pass before commit)
```

All content pipeline commands run from project root:

```bash
npm run validate     # Validate all content schemas
npm run build:index  # Rebuild graph.json from generated/ files
```

Generation scripts run from `src/web/`:

```bash
npx tsx scripts/automation/seedGenerator.ts --topic="Binary Search"
npx tsx scripts/automation/contentGenerator.ts --topic=binary-search
npx tsx scripts/automation/cosmosPusher.ts --topic=binary-search
```

## Data Flow

### Production mode (VITE_DATA_SOURCE=cosmosdb)
```
LeetCode GraphQL
  -> contentGenerator.ts
     -> for each seed problem, check Cosmos DB by `slug + topicSlug`
     -> if present for that topic: skip generation
     -> if missing for that topic: direct copy from LeetCode + Mistral Call 1 + Mistral Call 2
  -> Mistral Call 1 (content fields) + Call 2 (code.cpp)
  -> src/generated/{topic}.json (current run batch only)
  -> cosmosPusher.ts
     -> for each generated problem, check Cosmos DB for same-topic duplicate
     -> if same `topicSlug` already has same `slug` or `title`: skip push
  -> Azure Cosmos DB (serves data at runtime)
  -> cosmosAdapter.ts
  -> dataService.ts
  -> React components
```

### Local dev mode (VITE_DATA_SOURCE=local)
```
src/generated/{topic}.json (whatever batch files currently exist locally)
  -> npm run build:index (buildGraph.ts - simple flatten, no merge needed)
  -> src/web/public/data/graph.json (gitignored)
  -> localAdapter.ts
  -> dataService.ts
  -> React components
```

Cosmos DB is the production source of truth. `src/generated/` is a local batch artifact used by the push step and, when needed, by local graph builds.

## File Responsibilities (do not mix these)

| File | Responsibility | May import |
|------|---------------|------------|
| `seedGenerator.ts` | Fetch LeetCode problem list, call Mistral to select and categorize | `leetCodeClient`, `mistralClient`, `promptTemplates`, `types` |
| `contentGenerator.ts` | For each seed problem, checks Back4App by `slug + topicSlug`. Generates only missing same-topic problems using LeetCode copy + two Mistral calls, then writes the current run batch to `generated/{topic}.json`. | `leetCodeClient`, `mistralClient`, `promptTemplates`, `parseUtils`, `types` |
| `leetCodeClient.ts` | All LeetCode API calls (REST + GraphQL). Cache + session cookie management. | Nothing from project |
| `mistralClient.ts` | All Mistral API calls. Retry logic. | `config` |
| `promptTemplates.ts` | Prompt construction. Returns strings. No API calls. | `types` |
| `parseUtils.ts` | HTML sanitization, JSON parsing, schemaVersion check, field validation | `types` |
| `validator.ts` | Schema validation against JSON schemas. Throws on invalid. | `types` |
| `back4appPusher.ts` | Pushes the current generated batch to Back4App. Skips same-topic duplicates when the same `topicSlug` already has the same `slug` or `title`. | `types`, `config` |
| `firebasePusher.ts` | Push to Firebase Firestore (legacy, do not run) | `types`, `config` |
| `config.ts` | Read env variables, export typed config object | Nothing |
| `types.ts` | TypeScript interfaces only. No logic. | Nothing |
| `dataService.ts` | Defines data interface, switches adapter based on `VITE_DATA_SOURCE` | `back4appAdapter` or `localAdapter` |
| `cosmosAdapter.ts` | Cosmos DB REST calls. Used by frontend in production mode. | `config` |
| `cosmosClient.ts` | Cosmos DB client for querying and upserting documents. | `config` |
| `back4appAdapter.ts` | Back4App REST calls. Legacy. Not imported by active code. | `config` |
| `localAdapter.ts` | Reads `graph.json`. Used by frontend in local dev mode only. | Nothing external |
| `firebaseAdapter.ts` | Firebase Firestore calls. Legacy. Not imported by active code. | Firebase SDK |

## What a Good Change Looks Like

Adding a new topic:
1. Run `seedGenerator.ts --topic="New Topic"` to get the seed file
2. Run `contentGenerator.ts --topic=new-topic` to generate only the seed problems that are not already present in Cosmos DB for that topic
3. Review the generated batch if needed
4. Run `cosmosPusher.ts --topic=new-topic` to push the generated batch to Cosmos DB (production)
5. Run `npm run build:index` from root to sync local dev graph.json
6. `npm run lint` and `npm run build` from `src/web/` must pass

Adding a new frontend component:
1. Data must come from `dataService.ts` only
2. No hardcoded strings, topic names, or problem data
3. Follow the existing minimal, notebook-style UI patterns
4. `npm run lint` and `npm run build` must pass

Changing a prompt:
1. Edit `promptTemplates.ts` only
2. Re-run `contentGenerator.ts` for affected topics
3. Validate output before pushing

## What Not to Build

The following are explicitly out of scope:

- User authentication or accounts
- Progress tracking
- Code execution or online judge
- Community features, comments, or ratings
- Problem creation without LeetCode as source
- Any UI feature that does not directly improve DSA learning from beginner to DSA advanced

If you are considering adding something, ask: does this help a user go from LeetCode Easy to DSA advanced faster? If the answer is not clearly yes, do not build it.

- [ ] No new dependencies added without justification in PR description

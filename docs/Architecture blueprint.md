# DSA Cookbook - Architecture Blueprint

> Read this before writing a single line of code.
> This is the canonical reference for the platform architecture, data contracts, and agent workflows.

---

## 1. What This Platform Is

A **hybrid content generation platform** for DSA study. It serves:

- Problem statements pulled from LeetCode.
- Educational content per problem: intuition, key observations, pseudocode, C++ implementation, pitfalls (generated by AI AI)
- Topic-level content: patterns, prerequisites, subtopics, complexity, edge cases (generated by AI AI)

Best resource for: LeetCode interview prep easy to DSA advanced and beyond.

## 2. System Layers (Strict, No Mixing)

```
Layer 1 - Content Layer
  content/topics/{slug}.md          - Human-authored Markdown + YAML frontmatter
  content/problems/{slug}.md        - Human-authored Markdown + YAML frontmatter

Layer 2 - Generation Layer (scripts)
  src/web/scripts/automation/       - LeetCode fetch + AI generation pipeline
  src/generated/{topic}.json        - Current run batch output
  src/seeds/{topic}.json            - Problem lists per topic

  What contentGenerator.ts does:
    - For each seed problem, checks Cosmos DB by slug + topicSlug
    - If the problem already exists for that topic in Cosmos DB, skips generation
    - If missing for that topic, copies from LeetCode directly: statement, constraints, examples, hints
    - Generates via AI Call 1: key_observations, intuition, approach, pseudocode, pitfalls, complexity, connection_to_subtopic
    - Generates via AI Call 2: code.cpp
    - Writes only the newly generated problems for that run to src/generated/{topic}.json

Layer 3 - Validation Layer
  src/validation/                   - Schema enforcement, runs before any push
  npm run validate                  - Must pass before any commit or push

Layer 4 - Data Layer
  Azure Cosmos DB                   - PRIMARY: production database, serves frontend at runtime
  src/web/public/data/graph.json   - LOCAL DEV ONLY: mirrors Cosmos DB, built from src/generated/

Layer 5 - Rendering Layer
  src/web/src/                      - React 19 + Vite + TypeScript frontend
  No hardcoded content. Ever.
  Production: frontend fetches from Cosmos DB at runtime via dataService.ts
  Local dev: frontend reads from graph.json via localAdapter.ts
```

Generated by `seedGenerator.ts`. Human must not edit this.
`schemaVersion` is checked at the start of `contentGenerator.ts`. If the version does not match the current expected version, the script aborts and asks you to regenerate the seed.

```json

  "topic": "Binary Search",
  "topicSlug": "binary-search",
  "generatedAt": "2024-01-01T00:00:00Z",
  "problems": [
    {
      "platform": "LeetCode",
      "id": 153,
      "slug": "find-minimum-in-rotated-sorted-array",
      "title": "Find Minimum in Rotated Sorted Array",
      "category": "Search on Rotated Array"
    }
  ]
}
```

### 6.2 Generated Problem - inside `src/generated/{topic}.json`

Generated by `contentGenerator.ts`. This is a self-contained problem document for a problem generated in the current run. The topic file may contain only the newly generated problems for that run.

**Field sources:**
- Copied directly from LeetCode (no AI, no tokens): `statement`, `constraints`, `examples`, `hints`
- Generated by AI Call 1: `content.key_observations`, `intuition`, `logical_reasoning`, `pseudocode`, `connection_to_subtopic`
- Generated by AI Call 2: `code.cpp`
- Derived from LeetCode metadata: `title`, `leetcode_id`, `difficulty`, `tags`
- Assigned by pipeline logic: `topic_id`, `subtopic_id`, `source`, `rating`, `importance`

```json
{
  "schemaVersion": 1,
  "id": "find-minimum-in-rotated-sorted-array",
  "title": "Find Minimum in Rotated Sorted Array",
  "topic_id": "binary-search",
  "subtopic_id": "search-on-rotated-array",
  "leetcode_id": 153,
  "leetcode_slug": "find-minimum-in-rotated-sorted-array",
  "source": "LeetCode",
  "difficulty": "Medium",
  "importance": "Crucial",
  "rating": 1400,
  "difficulty_bucket": "standard",
  "tags": ["binary-search", "array"],
  "time_complexity": "O(log n)",
  "space_complexity": "O(1)",
  "pitfalls": [
    "Using linear scan instead of binary search defeats the purpose",
    "Off-by-one on the right boundary when array is not rotated",
    "Forgetting to handle the case where the array has a single element"
  ],
  "content": {
    "statement": "Given the sorted rotated array nums of unique elements, return the minimum element of this array.",
    "constraints": "n == nums.length\n1 <= n <= 5000\n-5000 <= nums[i] <= 5000\nAll the integers of nums are unique.",
    "examples": "Input: nums = [3,4,5,1,2]\nOutput: 1\n\nInput: nums = [4,5,6,7,0,1,2]\nOutput: 0",
    "hints": ["Array was originally sorted. Think about where the pivot of rotation is."],
    "key_observations": "The minimum is always at the rotation pivot. In any subarray [lo, hi], if nums[mid] > nums[hi], the pivot is to the right of mid. Otherwise it is at mid or to the left.",
    "intuition": "Binary search works here because rotation creates exactly one inflection point. By comparing mid to hi (not lo), we reliably identify which half contains the pivot without needing to know where the original sort began.",
    "logical_reasoning": "1. lo = 0, hi = n-1. 2. mid = lo + (hi - lo) / 2. 3. If nums[mid] > nums[hi], the left half including mid is fully sorted, pivot is in (mid, hi], so lo = mid + 1. 4. Otherwise pivot is in [lo, mid], so hi = mid. 5. Repeat until lo == hi. 6. Return nums[lo].",
    "pseudocode": "lo = 0, hi = n - 1\nwhile lo < hi:\n  mid = lo + (hi - lo) / 2\n  if nums[mid] > nums[hi]:\n    lo = mid + 1\n  else:\n    hi = mid\nreturn nums[lo]",
    "connection_to_subtopic": "This is the template for all rotated-array binary search problems. The right-boundary comparison transfers directly to LC 33 (search target in rotated array) and LC 81 (with duplicates)."
  },
  "code": {
    "cpp": "class Solution {\npublic:\n    int findMin(vector<int>& nums) {\n        int lo = 0, hi = nums.size() - 1;\n        while (lo < hi) {\n            int mid = lo + (hi - lo) / 2;\n            if (nums[mid] > nums[hi]) lo = mid + 1;\n            else hi = mid;\n        }\n        return nums[lo];\n    }\n};"
  }
}
```

## 5. Generation Pipeline

### Step 1 - Seed Generation

```
Input: topic name + LeetCode tags
Process:
  1. Fetch all LeetCode problems via REST API (cache 24h)
  2. Filter by topic tags
  3. Call AI to select best N problems with category labels
  4. Write schemaVersion field to output
Output: src/seeds/{topic}.json
```

### Step 2 - Content Generation

```
Input: src/seeds/{topic}.json
Guard: check schemaVersion matches SEED_SCHEMA_VERSION. Abort if mismatch.

For each problem (sequential, 1s delay between LeetCode fetches):

  0. Check Cosmos DB for the same topic using:
       where = { slug, topicSlug }
     If found: skip generation for that problem to avoid spending AI tokens again.

  DIRECT COPY FROM LEETCODE (no AI, no tokens):
  1. fetchProblem(slug) [leetCodeClient.ts] - requires LEETCODE_SESSION cookie
  2. Copy to generated document:
       content.statement   <- sanitizeHtmlContent(problem.content)
       content.constraints <- extracted from problem.content HTML
       content.examples    <- problem.exampleTestcases
       content.hints       <- problem.hints (array, can be empty)
       title               <- problem.title
       leetcode_id         <- problem.questionId
       difficulty          <- problem.difficulty
       tags                <- problem.topicTags[].name

  AI CALL 1 - Educational content:
  Input to prompt: sanitized statement (context), hints, tags, difficulty, topic
  Output fields: key_observations, intuition, logical_reasoning, pseudocode, connection_to_subtopic
  max_tokens: 64000
  On parse failure: skip problem, log slug + "content call failed"

  AI CALL 2 - Code:
  Input to prompt: C++ template from problem.codeSnippets, key_observations from Call 1
  Output fields: code.cpp only
  max_tokens: 64000, retry up to 3 times
  On failure after retries: skip problem, log slug + "code call failed"

  Merge direct copy + Call 1 + Call 2 into one complete ProblemContent document.
  Validate all required fields non-empty.

After all problems:
  Build the current run batch output.
  Write schemaVersion to output.

Output: src/generated/{topic}.json (newly generated problems for that run only)
```

### Step 3 - Validation (pre-push gate)

```
Input: src/generated/{topic}.json
Guard: check schemaVersion matches GENERATED_SCHEMA_VERSION. Abort if mismatch.
Process:
  Current implementation relies mainly on in-script field checks during generation and push.
  There is no standalone validated complete-topic snapshot workflow in the current code path.
Output: validation report. Push scripts call this before any write.
```

### Step 4 - Push to Cosmos DB (production)

```
Input: src/generated/{topic}.json (validated)
Process:
  Upsert the topic document by existing topic lookup.
  For each generated problem:
    - compute slug = leetcode_slug || id
    - query Cosmos DB for same-topic duplicate using:
        where = { topicSlug, $or: [{ slug }, { title }] }
    - if found for the same topicSlug: skip push
    - if not found for that topicSlug: POST to create
Output: pushed/skipped summary for the current batch
```

### Step 5 - Build graph.json (local dev sync)

```
Input: whatever generated batch files currently exist in src/generated/
Process:
  Read all generated files.
  Flatten into graph structure with index maps (byTopic, byDifficulty, byRating).
  Write schemaVersion to output.
Output: src/web/public/data/graph.json (local dev only, gitignored)
Run: npm run build:index (from root)
Run this after any generation if you want local dev to reflect the current local generated batch.
```

## 6. AI Prompt Design

### Problem Content Prompt (Call 1 of 2)

Generates only the educational content fields. Does not generate code. The statement is passed as context for AI to reason from - it does not appear in the output.


### Problem Code Prompt (Call 2 of 2)

Runs after Call 1. Receives `key_observations` from Call 1 to ground the implementation.


### Topic Content Prompt (single call)
Generate content for the topic in a singlr AI call.

### Seed Selection Prompt
This prompt is used to select the best problems for a topic. It generates a seed for the selected topic.

## 7. AI Client Contract

```typescript
// Single completion call
callLLM(prompt: string, systemPrompt: string): Promise<string>

// Config
model: 'AI-large-latest'
temperature: 0.3
max_tokens: 64000   // Full context window. Two separate calls per problem prevent truncation.

// Retry: 5 attempts, exponential backoff starting 30s
// On 429: respect retry-after header
// On final failure: throw, log slug and call number (1 or 2) for debugging
```

**Two-call rule**: Every problem generates exactly two AI calls - one for `content.*` fields, one for `code.cpp` Each call is focused, smaller, and independently retryable. If Call 1 fails, skip the problem. If Call 1 succeeds but Call 2 fails, retry Call 2 up to 3 times before skipping the problem. Never push a problem missing either content or code.

## 9. Validation Rules (enforced before any push)

### Problem validations

**Top-level fields:**
- `schemaVersion` matches `GENERATED_SCHEMA_VERSION` constant
- `id` is kebab-case, matches `leetcode_slug`
- `topic_id` matches a known topic slug
- `leetcode_id` is a positive integer
- `leetcode_slug` is non-empty string
- `difficulty` is one of: Easy, Medium, Hard
- `importance` is one of: Crucial, Optional
- `rating` is number in 1000-2200 range
- `tags` is non-empty array
- `time_complexity` is non-empty string
- `space_complexity` is non-empty string
- `pitfalls` has minimum 3 entries, each non-empty string

**`content` object - all fields required and non-empty:**

Copied from LeetCode (must be non-empty, no HTML tags):
- `content.statement`
- `content.constraints`
- `content.examples`

Generated by AI (must be non-empty):
- `content.key_observations`
- `content.intuition`
- `content.logical_reasoning`
- `content.pseudocode`
- `content.connection_to_subtopic`

Note: `content.hints` is allowed to be an empty array (some LeetCode problems have no hints).

**`code` object:**
- `code.cpp` - non-empty, must contain "class Solution"

### Topic validations
- `schemaVersion` matches `GENERATED_SCHEMA_VERSION` constant
- `id` is kebab-case
- `lc_rating_range` is array of two numbers, first less than second
- `prerequisites` is array (can be empty)
- `patterns` has minimum 1 entry
- `pitfalls` has minimum 3 entries, each non-empty
- `subtopics` array is present (can be empty)
- `content.introduction` is non-empty
- `content.key_patterns` is non-empty
- `content.common_pitfalls` is non-empty
- `content.when_to_use` is non-empty

## 10. Frontend Data Contract

The frontend touches data through exactly one file: `src/web/src/services/dataService.ts`

```typescript
// Public API - these are the only functions components may call
getTopics(): Promise<Topic[]>
getTopicDetail(id: string): Promise<TopicDetail>
getProblemDetail(id: string): Promise<ProblemDetail>

// Switches adapter based on VITE_DATA_SOURCE:
//   "cosmosdb" -> cosmosAdapter.ts -> Azure Cosmos DB REST API (production)
//   "local"    -> localAdapter.ts   -> graph.json (local dev)
```

**Production (`VITE_DATA_SOURCE=cosmosdb`):**
`cosmosAdapter.ts` makes REST calls to Azure Cosmos DB at runtime. Problem documents are complete and self-contained - no secondary fetches needed.

**Local dev (`VITE_DATA_SOURCE=local`):**
`localAdapter.ts` reads `graph.json`. Run `npm run build:index` after any `contentGenerator.ts` run to keep local data in sync.

Components must never:
- Import any adapter directly
- Import Parse SDK or Firebase SDK
- Call any external API directly
- Have hardcoded topic or problem data

## 12. Error Handling Contracts

### Generation errors
- LeetCode blocked (403/429, no cache): log slug and reason, skip problem, continue. Report blocked slugs at end.
- LeetCode session expired (401): abort entire pipeline with message to refresh `LEETCODE_SESSION`.
- LeetCode fetch fails (network): retry 3 times with 2s delay, then skip problem.
- AI Call 1 returns invalid JSON: log slug, skip problem. No recovery.
- AI Call 2 returns invalid JSON: retry up to 3 times, then skip problem. Log slug + "code call failed".
- AI rate limited (429): respect retry-after header, up to 5 retries with exponential backoff.
- `schemaVersion` mismatch on seed or generated file: abort with clear message identifying the file.

### Push errors
- Validation fails for document: skip that document, log field + document ID, continue.
- Cosmos DB write fails: log document ID and HTTP status, continue, report at end.
- Never push a topic document if zero of its problems pushed successfully.

### Local graph build errors
- Generated file `schemaVersion` mismatch: abort `buildGraph.ts` with filename.
- Generated file missing or corrupt: abort with filename.

### Cosmos DB Setup (one-time, before first push)

In the Azure Cosmos DB dashboard, set a unique key constraint on the `id` field for both `topics` and `problems` containers. This makes upserts atomic - POST fails with duplicate key error, script then PUTs to the existing document. Without this, concurrent runs or crashes mid-push can create duplicate documents.

### Full pipeline for a new topic

```bash
# 1. Generate
cd src/web
npx tsx scripts/automation/seedGenerator.ts --topic="Sliding Window"
npx tsx scripts/automation/contentGenerator.ts --topic=sliding-window

# 2. Push to production
npx tsx scripts/automation/cosmosPusher.ts --topic=sliding-window

# 3. Sync local dev
cd ../..
npm run build:index

# 4. Verify locally (set VITE_DATA_SOURCE=local in .env)
cd src/web
npm run dev
```
